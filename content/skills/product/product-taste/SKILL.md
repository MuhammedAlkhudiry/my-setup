The owner's recurring product judgment. $ux-ui owns the design workflow and checks; this file says what the owner will accept.

## Product judgment

- Open with bold options. Safe variations of today's design get rejected; wild ideas are welcome before narrowing.
- Cut every concept, step, mode, or control users do not need. For each element, be ready to answer "why was it added?"
- Tie each feature to the core loop and give users a reason to choose it over the existing simple path. A secondary feature stays
  secondary; never let it reshape the core screen.
- Design for ordinary users and the full range of real data: odd shapes, the largest realistic sizes, production samples. A design
  that only suits experts, or only the sample, fails.
- Research how comparable products solve it before proposing a direction.
- Anchor new UI in something users already know, without cloning it.
- Treat smoothness and speed as features: interactions are instant, continuous, and live, never stepped or delayed.
- Decide by user value, not build cost; cost is not a reason to lower the bar.
- Drop limits, caps, and waits you cannot justify from user value.
- Ship fewer things, each complete. Defer whole parts to the roadmap rather than shipping a thin or tacked-on version.
- Plan how users find and understand a new feature, and what changes for existing users, not only for new ones.
- Let users skip or opt out of optional layers instead of forcing them through.

## UI taste

- Calm screens. Too many colors, lines, badges, or words reads as noise; cut before adding.
- Keep frequent actions on the surface; avoid "More" screens. Fold only secondary tools.
- Use one pattern for the same job everywhere: the same flow, control, and component. Reuse an existing pattern before inventing one.
- Write copy in the user's words: short, warm, natural, never stiff or literal. Characters speak like characters, not feature lists.
- Make art look made for its place: in the product's style, legible at real size, part of its scene rather than pasted on, with no gaps
  or artifacts.

## Launching

- Put new features behind an internal-only flag so the owner can try them in real builds before release.
- Make new features measurable: usage events and an admin view, judged by whether users come back, not by sign-ups.
